# コーディング規約

コードを書く前にこの規約を読み、書き終えたら末尾のチェックで自己確認する。
規約と既存コードが食い違う場合は、勝手にどちらかに寄せず、ユーザーに確認する。

## 命名

- 変数・関数は camelCase、クラス・型は PascalCase、定数は UPPER_SNAKE_CASE
- 真偽値は `is` / `has` / `can` で始める（例: `isActive`）
- 略語は避ける。`usr` ではなく `user`、`cnt` ではなく `count`
- 関数名は動詞で始める（`getUser`, `calculateTotal`）

## フォルダ構成

```
src/
  features/<機能名>/   # 機能ごとにまとめる（画面・ロジック・テストを同じ場所に）
  shared/              # 2つ以上の機能で使う部品だけ
  config/              # 設定値（環境変数の読み込みはここだけ）
```

- 新しい機能は `src/features/` の下にフォルダを作る
- `shared/` に入れるのは、実際に2か所以上から使われてから

## 関数とファイルの大きさ

- 1関数はおおむね40行以内。超えたら分割を検討する
- 1ファイルはおおむね300行以内
- 引数が4つ以上になったらオブジェクトにまとめる

## エラー処理

- エラーを握りつぶさない。`catch` したら、ログを出すか、呼び出し元に投げ直す
- ユーザー向けメッセージと、ログ向けの詳細を分ける
- 外部API呼び出しには必ずタイムアウトを設定する

## ログ

- `console.log` を本番コードに残さない。共通のロガーを使う
- ログに個人情報・トークン・パスワードを出さない

## 秘密情報

- APIキー・パスワード・接続文字列をコードに直書きしない。環境変数から `src/config/` 経由で読む
- `.env` ファイルは読まない・内容を出力しない・コミットしない

## コメント

- 「何をしているか」ではなく「なぜそうしているか」を書く
- コメントアウトしたコードを残さない（Gitに履歴がある）

## 書き終えたらのチェック

- [ ] 命名規則に沿っているか
- [ ] 置き場所は `features/` か `shared/` か、理由を説明できるか
- [ ] 握りつぶしている `catch` はないか
- [ ] 秘密情報の直書き・`console.log` の残りはないか
- [ ] 対応するテストがあるか（なければ test-driven-development に戻る）
